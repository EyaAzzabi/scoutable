01 — The intelligence

Embeddings, not filters.

A filter can tell you who is under 23 and costs less than €500k. It cannot tell you who plays like the winger you just lost, or who is priced below what they are worth. Both of those are model questions.

Vector embeddings

Every player is encoded as a 21-dimension "DNA" vector and every scouting report as a 384-dimension text embedding, both in pgvector behind HNSW cosine indexes. Playing style becomes geometry — so "who plays like this player" is a nearest-neighbour query, not a set of filters.

Gradient-boosted valuation

An XGBoost regressor predicts what each player should cost given age, role, output, minutes and league strength. The residual against the real market value is the arbitrage signal — it currently flags 3,163 under-priced players.

A ranking model, not a sort

Recommendations blend fit × quality × value — embedding distance, peer-group percentile and model residual — and expose all three. The decision stays contestable instead of arriving as one opaque score.

A grounded RAG agent

A tool-calling LLM that answers in plain English, never writes SQL, routes each question to one of seven retrieval tools, and cites every player by id — with an eval that fails if it cites a player it did not actually retrieve.

Local semantic retrieval

Reports are embedded on-machine with sentence-transformers MiniLM, so qualitative questions the SQL filters cannot express — "an aggressive ball-winner who is under-priced" — are answerable at no per-call cost, and the notes never leave the box.

Probabilistic entity resolution

The three sources share no common player id. Linking them is blocking on birth year → RapidFuzz name scoring → a club crosswalk → a merged golden record with a confidence score. Everything above depends on it: without it there is no player to embed.

How I know it works.

Anyone can ship a model. What makes one trustworthy is that every claim above has a command that tests it — measurement lives in the CLI, not in a notebook that ran once.

The honest reading of that 1.00 / 1.00

The gold set is not hand-labelled — it is built automatically from records whose normalised name maps to exactly one canonical player. So the test proves the fuzzy path recovers every link the exact path already gets right: a real regression guard, and not evidence of accuracy on the hard cases — transliteration variants, ambiguous names, missing birth years — which that construction excludes by definition. Measuring those needs hand-labelling, which is the obvious next work.

Measurement is what found the one real bug in the ranker

reco-eval originally reported a mean quality lift of just +0.066, and negative for strikers and defensive midfielders — the recommender was returning players slightly worse than league average, while quality carried twice the nominal weight of value. The two components were normalised against fixed ranges of very different usefulness: season ratings occupy only ~6.2–7.8 of the 5.5–8.5 window the quality scaler assumes, while the value scaler saturates at 2.0×, which is extremely common in these leagues. Value therefore had the larger effective spread despite the smaller nominal weight, and the ranker drifted toward cheap players — which are, on average, slightly worse ones. Ranking each component against the actual candidate pool makes effective weight equal nominal weight.

02 — What it does

Six surfaces, one model underneath.

Every board reads from the same golden records, the same DNA vectors and the same fair-value model. Plans decide which of them you can open.

Silver

A recommendation engine that shows its working

Describe a need, a budget and optionally a playstyle target, and every result breaks into three visible bars rather than collapsing into one score — because a scout has to be able to disagree with the model on a specific axis.

  • fit — cosine distance from the requested DNA profile
  • quality — percentile within the player's own peer group
  • value — market price against the model's fair value
Free

Profiles ranked against a real peer group

Percentiles are computed against players in the same role and the same league, never a global pool. Each merged record carries a confidence score, so a profile stitched from three disagreeing sources never pretends to be as solid as one where they agree.

Gold

The contract-expiry radar

Players running down their contracts, soonest first — the ones who can be signed for a fee of zero if you move before somebody else does, each with the same fair-value verdict attached.

Gold

An assistant that can only answer from the data

It never writes SQL. It supplies values against a typed schema that compile to a parameterised query with a hard row cap, and every player it names is cited by id — with an eval that fails the build if it cites one it did not actually retrieve.

  • Seven retrieval tools; routing is the model's tool choice
  • Notes embedded locally (MiniLM, 384-dim) into pgvector — no key, no per-call cost
  • Note text fenced as untrusted, with an injection case in the eval set
  • Redis tool cache: a repeat question goes 2,134 ms → 1.3 ms

/players — every card carries the model's verdict and the record's confidence, not just the market price.

03 — How the data gets there

Three sources that share no identifier.

Each source is an isolated adapter that stores its verbatim payload in a raw zone first — auditable and replayable, so a parser bug is fixed by re-normalising rather than re-scraping.

Entity resolution

Birth-year blocking → RapidFuzz name scoring → a club crosswalk → a merged golden record with a confidence value. Anything below threshold goes to a human review queue rather than being silently guessed, and precision/recall are scored against a hand-built gold set.

Player DNA

21 dimensions — 11 numeric plus 8 position sub-role one-hots — z-scored within each league, L2-normalised, stored in pgvector behind an HNSW cosine index. Search is role-gated, and neighbours measure ~40% closer in rating than random.

Fair value

An XGBoost regressor predicts what a player should cost given age, role, output, minutes and league strength. The residual is the arbitrage signal — currently 3,163 players priced below what the model expects.

04 — Engineering decisions

The parts that were judgement, not typing.

The paywall has exactly one source of truth

The feature matrix lives in a single module and is served verbatim by GET /billing/plans. The ticks on the pricing page and the gate the API enforces are literally the same table, so they cannot drift. Adding a feature is one row — pricing, nav locks and the API gate all follow.

Gating returns 402, not 403

A signed-in user on too small a plan gets a payload naming the feature and the plan that unlocks it — enough for the UI to render an upgrade panel where the data would have been. Frontend gating is UX only; the same key is enforced server-side, so editing local state gets you a 402 rather than data.

Refresh tokens are opaque, hashed and rotated on every use

A stolen token works at most once, and the theft surfaces as an unexpected sign-out. current_user re-reads the user row instead of trusting the plan claim in the JWT, so a downgrade or a ban takes effect immediately rather than at token expiry.

The sign-in throttle keys on IP, not e-mail

Keying on the e-mail address would let an attacker lock a known victim out of their own account.

Stripe's webhook moves a user between plans — never the redirect

The redirect back from Checkout only proves the browser came back; the webhook proves the money settled. With no Stripe key the same endpoints run in demo mode and mark the row plan_status="demo", so an account upgraded without payment is never mistaken for a paying customer.

Player portraits pass three independent checks

Photos are hot-linked from third-party CDNs, so a string scraped out of somebody else's HTML ends up in an <img src> in a signed-in user's browser. It is validated on write, on read, and again by CSP in the browser — each layer assuming the others failed. The allowlist is exact-match, not a suffix check, because endswith would happily accept img.transfermarkt.technology.evil.com.

The image pins xgboost-cpu on Linux on purpose

From XGBoost 3.x the plain wheel hard-depends on the NVIDIA CUDA runtime — nvidia-nccl alone is 252 MB — adding close to a gigabyte to the image and to every deployment pull, for a model that trains and scores on CPU.

Two visual registers, deliberately

The signed-in app is a card system built for scanning data. The landing page is editorial — mono micro-labels, hairline rules, a much tighter display scale — because a marketing page built out of the app's own cards is what makes a product look templated. Every number on it is live from the API, so the page cannot claim something the database does not back.

DB-backed tests run inside a rolled-back transaction. ruff lints, alembic check fails the build on model/migration drift, tsc --noEmit covers the frontend.

Measured, not asserted

Entity resolution scored against a gold set, recommendation role-purity and quality lift evaluated, DNA neighbour quality quantified, assistant answers checked for citation grounding.

One-command deploy

The full stack behind Caddy, which provisions and renews TLS itself. Only Caddy publishes ports, so Postgres and Redis are unreachable from the internet. Migrations run on API start; nightly pg_dump with 14-day retention.
